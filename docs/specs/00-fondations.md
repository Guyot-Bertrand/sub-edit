# Subproject 0 — Foundations

**State:** completed on 2026-08-05
**Milestone:** `0 — Fondations`

## Goal

Lay down the structure, the build chain and the verification net of the
project, before any line of business code. The question this subproject
answers: **how do we judge that the code produced is good, beyond the fact that
it compiles?**

The answer fits in one command, `make check`, run identically locally and in
continuous integration.

## Context

`subedit` rewrites [Gaupol](https://github.com/otsaloma/gaupol) — a GTK/Python
subtitle editor — in C++23 + Qt 6, aiming at feature parity. The inventory of
the features to cover is in [`gaupol-reference.md`](gaupol-reference.md). The
work is split into phases; this one is the first.

The design rules that apply to all the code — typed data models, explicit
memory ownership, abstraction where the variation is known — are in
[`../principes-de-conception.md`](../principes-de-conception.md). This
subproject mechanises the verifiable part of them: `make check` must refuse what
these rules forbid, rather than rely on vigilance during review.

Performance is a **cross-cutting design goal** — choosing data structures,
algorithms and tools that do not waste — and not the fix of a measured
slowness. That is why benchmarks are tooled from the foundations rather than
added after the fact.

## Scope

**Included:** repository layout, code conventions, CMake and presets, the
`make` facade, test and benchmark framework, static analysis, sanitizers,
coverage, GitHub Actions CI, git hooks, issue and PR templates, CHANGELOG
generation, documentation skeleton, retro-documented ADRs.

**Deliberately excluded:** active Conan and vcpkg, Doxygen generation,
packaging, automated publishing, multi-compiler matrix, multiple operating
systems. Each has a trigger identified further down; none is triggered today.

### Architecture rule: all useful code is in a library

An executable comes down to a `main`, the parsing of its arguments if needed,
and calls into the libraries. No functional logic in `src/exe` — not even in the
graphical interface: the main window, the table model, the dialogs and the
actions live in `subedit_gui`, and `src/exe/gui/main.cpp` is limited to
instantiating `QApplication`, building the window and starting the event loop.

The benefit is direct: what is in a library is testable, Qt code included,
driven by Qt Test.

### Libraries

```
src/lib/subedit/core/    subedit_core   model, formats, operations — no Qt dependency
src/lib/subedit/cli/     subedit_cli    argument parsing and commands, on top of core
src/lib/subedit/gui/     subedit_gui    Qt interface, on top of core
```

Each direct child of `src/lib/subedit/` is a CMake target. If `core` grows too
big, it splits without affecting the rest.

**Eight invariants checked by CI**, all by
[`check-architecture.sh`](../../src/scripts/check-architecture.sh):

1. `subedit_core` depends on no Qt symbol and no UI.
2. `src/exe/**/main.cpp` contains no class, no algorithm and no direct system
   call.
3. the scripts in `src/scripts/` are executable in the git index.
4. a version tag on `HEAD` agrees with `project(VERSION)`.
5. no test case name starts with a dash.
6. nothing under `src/` reads the reference repository.
7. nothing under `src/` is generated by a tool.
8. nothing under `model/` includes `format/`, `io/`, `edit/` or `command/`.

**Only two date from this phase.** The other six were added afterwards, each
because its absence had cost something real — see "What moved during the
phase" for the first three; phase 4 for the one that protects the reference
repository; the tooling of phase 5 for the one that keeps generated files out,
`moc` producing them by the dozen; and
[ADR 0018](../adr/0018-vocabulaire-des-formats-dans-le-modele.md) for the last
one — the boundary between the model and the operations had already faded once
without anything reporting it.

### Includes

A single include root: `src/lib/`. Every include internal to the project is
qualified and absolute.

```cpp
#include <subedit/core/model/subtitle.hpp>
```

No relative path (`../`), no ambiguity, and the targets stay movable. What is
internal to a library goes into a `detail/` subfolder; the rest is the public
API. Headers and sources sit side by side — an `include/` + `src/` split would
duplicate the tree without bringing anything to an application repository.

### Tests

`src/test/` mirrors the library tree:

```
src/test/unit/core/model/subtitle_test.cpp
src/test/bench/core/format/srt_bench.cpp
src/test/data/                              reference subtitle files
src/test/tools/                             the programs the tests launch
```

`src/test/tools/` breaks the symmetry because it mirrors nothing: these are not
tests, but **the third parties a test needs to bring into existence**. The
first is `fake_player.cpp`, which came in with phase 6 — a program that writes
its arguments, complains on demand and stops. It served an external video
player, which the framing of phase 6 removed in favour of an embedded player;
it now stands in for `ffprobe`, which asks exactly the same things of it. What
a test wants from an outside program is to know which arguments it was launched
with and to be able to make it fail — the real one would cost what it costs and
would not be installed everywhere.

Nothing shipped contains them: no install target names them.

One test binary per library, registered in CTest through
`catch_discover_tests` so that each case is visible and can be filtered
individually.

`src/test/e2e/` is the exception to this symmetry: it mirrors `src/exe/`, not
`src/lib/`. These tests do not link the logic they check — they launch the real
binary through `posix_spawn`, without a shell, and compare standard output,
standard error and exit code. Each case cites a requirement of
[`docs/exigences.md`](../exigences.md) through a Catch2 tag, which
`src/scripts/check-requirements.sh` checks against the registry.

They are not registered in CTest under the `coverage` preset: `subedit-cli` is
instrumented there, and every invocation would inflate the coverage of
`src/lib` without any unit test having been written for that code. See
[ADR 0014](../adr/0014-registre-d-exigences.md).

## Code conventions

| Element | Convention |
| :------ | :--------- |
| Files | `snake_case.hpp` / `snake_case.cpp` |
| Namespaces | `subedit::core`, lowercase |
| Types | `PascalCase` |
| Functions and variables | `camelCase` |
| Private members | `m_` prefix |
| Compile-time constants | `kPascalCase` |

Mixing conventions between the core and the Qt code would be worse than either
style; `camelCase` therefore follows the Qt API across the whole project. These
rules are **enforced mechanically** by clang-tidy's
`readability-identifier-naming`, not left to vigilance.

Format: `.clang-format` derived from the LLVM style, 4-space indentation,
100-column limit, pointers aligned left.

Standard: **C++23** since [`../adr/0007-cpp23-et-std-expected.md`](../adr/0007-cpp23-et-std-expected.md),
C++20 at the start of this phase. Requires clang-tidy ≥ 19. **C++ modules are
excluded** — tool support, clang-tidy and the generators in particular, is not
mature.

## Build

CMake ≥ 3.28 (the version present on the machine). Ninja is the preferred
generator, but **the presets do not pin it**: the `make` facade selects it if
it is installed and falls back to Unix Makefiles otherwise. Pinning it would
make the project unbuildable on a machine that does not have it yet, for no
gain.

### Presets

| Preset | Content |
| :----- | :------ |
| `dev` | Debug, warnings as errors, tests enabled — the default preset |
| `asan` | Debug + AddressSanitizer + UndefinedBehaviorSanitizer |
| `coverage` | Debug + coverage instrumentation |
| `release` | RelWithDebInfo + LTO |

`ccache` is used if present, ignored otherwise.

### Registering the end-to-end tests

The tests in `src/test/e2e/` are built under all four presets — their warnings
are ours everywhere — but are registered in CTest only under **`asan` and
`release`**, through a declarative cache option, `SUBEDIT_REGISTER_E2E`
(`CMakeLists.txt`), set to `ON` explicitly by these two presets in
`CMakePresets.json` and nowhere else. Choosing a declarative flag rather than a
compound `if()` on `CMAKE_BUILD_TYPE` and `SUBEDIT_SANITIZERS` is deliberate: it
can be reread without reconstructing the reasoning.

- **`dev` does not register the end-to-end tests.** `dev` and `asan` are both
  Debug builds; `asan` is strictly more informative (AddressSanitizer,
  UndefinedBehaviorSanitizer, LeakSanitizer), so registering them under `dev`
  as well would only add one more run, with no new signal. **Practical
  consequence: `make test` no longer exercises the end-to-end harness; `make
  asan` is now the fastest way to do so in the development loop.**
- **`release` registers them**: it is the mode that ships, the binary a user
  actually launches. `make e2e` configures and builds this preset, then runs
  only these tests, filtered by the CTest label `e2e`
  (`catch_discover_tests(... PROPERTIES LABELS e2e)`) rather than by test
  name — a unit test name that came close would not fool it.
- **`coverage` does not register them**, for the reason already in place
  before this mechanism: under this preset, `subedit-cli` is instrumented too,
  and every invocation would inflate the coverage of `src/lib` without any unit
  test having been written for that code. See
  [ADR 0014](../adr/0014-registre-d-exigences.md).

### The `make` facade

CMake is verbose to use; the `Makefile` adds no build logic, only shortcuts.
**Since #269, it no longer carries any either**: each step lives in
`src/scripts/gate/`, one per file, and `src/scripts/gate.sh` holds the order.
The targets remain the interface one types, reduced to a single call. Two
targets govern everything else: **`make check`**, the gate that CI enforces on
every push, and **`make check-local`**, the one command to run before opening
a pull request. Both are described in detail below; the table gives the role of
each target, the CMake preset it configures, what it chains, and its
parameters.

| Target | Role | Preset | Chains | Parameters |
| :----- | :--- | :----- | :----- | :--------- |
| `make help` | prints this list, generated from the `##` comments of the `Makefile` | — | — | — |
| `make setup` | installs the missing toolchain and the git hooks | — | — | — |
| `make build` | configures and builds | `dev` | — | `JOBS` |
| `make test` | builds and runs the tests, **except end-to-end** — see `make asan` | `dev` | — | `JOBS` |
| `make format` | applies `clang-format` to the tracked files | — | — | — |
| `make format-check` | checks the format without modifying, `--Werror` verdict | — | — | — |
| `make tidy` | static analysis — `clang-tidy` hooked to the compilation of each source | `tidy` | — | `JOBS` |
| `make arch` | checks the architecture invariants (`check-architecture.sh`) | — | — | — |
| `make parallelism` | checks that no parallelism bypasses `$(JOBS)` (`check-parallelism.sh`) | — | — | — |
| `make fixtures` | checks the video fixtures in `src/test/data/videos/` against the table of `video-fixtures.sh` | — | — | — |
| `make requirements` | checks `docs/exigences.md` against the tags of the end-to-end tests (`check-requirements.sh`) | `dev` | — | `JOBS` |
| `make e2e` | runs **only** the end-to-end tests, filtered by the CTest label `e2e` | `release` | — | `JOBS` |
| `make asan` | runs the tests under ASan/UBSan/LeakSanitizer — end-to-end tests included | `asan` | — | `JOBS` |
| `make coverage` | measures the coverage of the libraries, fails if the number of uncovered lines rises compared with the record | `coverage` | — | `JOBS` |
| `make ratchet` | records the measured coverage as the new ratchet in the record | — | — | — |
| `make bench` | runs the benchmarks, appends the figures to the log `docs/mesures/performances.md`, verdict read by a human, not binary | `release` | — | `JOBS` |
| `make check` | **quality gate — CI, FROZEN, described below** | `dev`/`asan`/`coverage` through its sub-targets | `format-check`, `arch`, `build`, `tidy`, `asan`, `coverage` | `JOBS` |
| `make check-local` | **the one command before a pull request, described below** | all the presets its sub-targets use | `parallelism`, `fixtures`, `manual-check`, `requirements`, `e2e`, `bench` | `JOBS` |
| `make verify-gates` | proves that `check` and `check-local` each fail on their injected defects | `tidy` and those of its proofs | — | — |
| `make changelog` | regenerates `CHANGELOG.md` from the commit history | — | — | — |
| `make clean` | removes `build/` | — | — | — |

**A suite can be resumed in the middle**, which the chain of sub-`make` calls
could not do — and which cost paying thirty-four minutes again when the
thirty-fifth broke:

```console
$ ./src/scripts/gate.sh --list
$ ./src/scripts/gate.sh check --from coverage
$ ./src/scripts/gate.sh check --only tidy
```

An unknown step name, or a combination of filters that keeps nothing, makes the
invocation fail rather than play none: returning zero without doing anything
would be a green gate that checked nothing.

`make e2e` and `make bench` both configure and build the `release` preset:
running one after the other recompiles nothing *of the library* —
`subedit_core` is an object shared between the two. Each links its own
executable (`subedit_e2e_test`, `subedit_bench`), so linking and compiling the
files specific to that executable remain to be done.

**Why two gates.** `make check` is what CI runs, identically, on every push by
every person — it is its only net, and whatever goes into it gates everyone. A
check that is useful but too costly, or too specific to the development
workstation, to gate every push (the controlled parallelism check, the
requirement registry check, the end-to-end harness, the benchmarks) therefore
has no place in `make check`: it goes into `make check-local`, a target CI
never runs and that one launches oneself before opening a pull request. **The
command to remember before opening a pull request is `make check-local`.**

### Controlled parallelism

Every site of parallelism in the facade — compilation, `clang-tidy`, LTO of the
benchmarks — goes through a single variable, `JOBS`, whose default value is
**two cores locally**. The development machine runs other projects at the same
time, and unbounded parallelism there causes tests to fail on timeouts; two is
the agreed ceiling, which can be raised case by case with `make build JOBS=8`
without touching the `Makefile`. **CI chooses for itself** —
`.github/workflows/ci.yml` calls `make check JOBS=$(nproc)` explicitly, its
machine being its own.

The discipline would be worthless without a mechanical check:
`make parallelism`, which runs `src/scripts/check-parallelism.sh`, refuses any
`Makefile` recipe where `-j` or `-P` is not followed by `$(JOBS)`, any script in
`src/scripts/` that would introduce its own parallelism (hard-coded `-j`/`-P`,
`xargs -P`, a call to `nproc`, a command sent to the background by a trailing
`&`), and any hard-coded `-flto=` in `cmake/*.cmake` or `CMakeLists.txt`
outside the `SUBEDIT_LTO_JOBS` mechanism. This check lives in
`make check-local`, not in `make check`: it protects the development
workstation, not CI, which already bounds its own parallelism otherwise.

## Dependencies

Resolved by `find_package` on system packages, with two exceptions.

| Dependency | Origin | Required for |
| :--------- | :----- | :----------- |
| Catch2 v3 | `FetchContent` | tests and micro-benchmarks |
| Qt 6 | system packages | subproject 5 |
| libmpv | system packages | phase 6 — the embedded player, see [ADR 0020](../adr/0020-libmpv-pour-le-lecteur-integre.md) |
| ~~PCRE2 or RE2~~ ICU | system packages | phase 12 — **settled in favour of ICU**, already present: [ADR 0036](../adr/0036-icu-pour-les-motifs-de-correction.md) |
| ICU | system packages | encodings, phase 8 |
| ~~hunspell~~ Enchant 2 | system packages | phase 12 — the spell checker, [spec 12](12-correction.md), D6 |

Catch2 is an exception because it compiles in a few seconds and its version
must be identical everywhere; pinning it keeps a distribution update from
breaking the tests.

libmpv is an exception in another way: it is indeed a system package, but it
does not publish a CMake configuration file — only an `mpv.pc`.
`pkg_check_modules(… IMPORTED_TARGET mpv)` derives `PkgConfig::mpv` from it, a
target that carries its include paths and link flags as a Qt target would.

No C++ package manager is set up. Since the CMake is written around
`find_package`, adopting Conan or vcpkg later is nearly free — both work by
interposing themselves precisely on that mechanism. The trigger would be the
actual Windows port.

`src/scripts/setup-toolchain.sh` installs what is missing on an Ubuntu
machine: ninja, clang-tidy, clang-format, gcovr, ccache, git-cliff, gh, jq,
pkg-config, CLI11, the Qt 6 development packages, `libmpv-dev`, and `ffmpeg`
for its `ffprobe`.

The last three are not dependencies of the same nature as the others. Qt 6 and
libmpv are linked into the binary, hence mandatory to build — the `--with-qt`
mode, which claimed otherwise for Qt, disappeared in phase 5. `ffprobe` is an
executable that one launches: the project requires it of a development
machine, never of a user, and the code carries the branch for its absence.

`pkg-config` is on the list for libmpv, which is found through it: without it,
`find_package(PkgConfig REQUIRED)` fails on a bare machine.

**Qt Multimedia was on it, and no longer is.** It had been declared in phase 5
"for the preview of phase 6"; ADR 0020 settled the video backend in favour of
libmpv, and nothing had ever linked it. A dependency nobody uses is not free:
it sits in CI's package cache, and the line that declared it announced a use
that will never exist.

## The quality gate: `make check`

Five steps, binary verdict, no tolerance:

1. **Format** — `clang-format --dry-run --Werror` on all tracked files.
2. **Compilation** — `dev` preset with `-Wall -Wextra -Wpedantic -Wconversion
   -Wshadow -Wnon-virtual-dtor -Wold-style-cast -Wcast-align -Wunused
   -Woverloaded-virtual -Wnull-dereference -Wdouble-promotion -Werror`.
3. **Static analysis** — `clang-tidy`: the `bugprone-*`, `performance-*`,
   `modernize-*`, `readability-*`, `misc-*` families, plus a selection of
   `cppcoreguidelines-*`. Including, explicitly, the checks that mechanise the
   memory ownership rules of the design principles:
   `cppcoreguidelines-owning-memory`, `cppcoreguidelines-no-malloc`,
   `cppcoreguidelines-special-member-functions`, `modernize-make-unique`,
   `modernize-avoid-c-arrays`, `misc-const-correctness`. The exclusions are
   listed in `.clang-tidy` **with their justification in a comment**; an
   unjustified exclusion is a defect. The same goes for the two local `NOLINT`s,
   whose list and reason `.clang-tidy` carries: an exemption that can only be
   read where it applies ends up not being read at all.

   **It is hooked to the compilation of each source, under the `tidy`
   preset** — `cmake/Tidy.cmake`, issue #269. What decides to reanalyse a file
   is the build system: its source, a header from its dependency file, or its
   command line. There is therefore nothing to compute, nothing to pass, and a
   change that alters no compilation input mechanically costs nothing. The
   content of `.clang-tidy` and the version of the binary, which Ninja would
   not see, enter the flags as a fingerprint.

   **It analyses the headers, which it had never done.**
   `HeaderFilterRegex` matched nothing from the repository root, and the preset
   fixed that by construction — its working directory being the build tree.
   Corollary: a directory's `.clang-tidy` governs only the `.cpp` files of that
   directory, never the diagnostics raised in a header.
4. **Tests** — run under the `asan` preset, so that any memory error or
   undefined behaviour fails instead of going unnoticed. The preset also
   enables **LeakSanitizer**: a leak makes the tests fail, it is not discovered
   six months later.
5. **Coverage** — the number of lines of `src/lib/` that the tests do not
   exercise must not rise. The record lives in
   [`docs/mesures/couverture.md`](../mesures/couverture.md); the gate fails on
   a rise, naming the files concerned, and suggests `make ratchet` on a fall. A
   line count rather than a percentage: a percentage goes up as soon as
   well-tested code is added, which would tighten the ratchet without anyone
   having decided so. See [ADR 0015](../adr/0015-memoire-des-mesures.md). The
   executables stay excluded from the calculation: the architecture rule
   empties them of anything worth covering.

**CI calls `make check`, and nothing else.** No step is copied into the YAML.
It is the only way for the local net and the remote net to stay identical in
six months.

## The `make check-local` target: the one command before a pull request

`make check` is what CI runs — `.github/workflows/ci.yml` calls only that
target. A check one wants to see pass before opening a pull request, but does
not want to see gate every push by every person, therefore has no place in
`make check`: it goes into `make check-local`, a separate target that CI never
runs.

`check-local` chains six steps, in this precise order — the cheapest first, so
that a defect costs seconds rather than the whole chain:

1. **Controlled parallelism** — `make parallelism`: `check-parallelism.sh`
   refuses any site of parallelism, in the `Makefile`, in `src/scripts/` or in
   `cmake/`, that bypasses `$(JOBS)` or `SUBEDIT_LTO_JOBS`. A grep, under a
   second — hence its place at the head: making it wait behind a step that
   compiles would cost a hard-coded `-j 8` the time of that build before it is
   heard. See [“Controlled parallelism”](#controlled-parallelism) above.
2. **Video fixtures** — `make fixtures`: `video-fixtures.sh --check` checks the
   containers in [`src/test/data/videos/`](../../src/test/data/videos/) against
   the table that says what they declare — frame rate, duration, maximum size.
   Two calls to `ffprobe`, under a second, and nothing to build. It is here and
   not in `make check` for the reason that holds for the rest of this list, and
   **with the same consequence to be aware of: CI will not see a fixture that
   has drifted.** The defect is born when the fixture is remade, hence on the
   workstation that remakes it, hence before the pull request.
3. **Manual examples** — `make manual-check`: `generate-manual.sh --check`
   compares each example block with what the command actually writes. It is
   here and not in the gate because putting it there would bring
   `docs/manual/**` into the scope of `check`, from which `docs/**` is
   excluded, and a touch-up of prose would reopen fifteen minutes of
   compilation.
4. **Requirements** — `make requirements`: `check-requirements.sh` checks the
   registry [`docs/exigences.md`](../exigences.md) against the tags of the
   end-to-end tests, in both directions: an `implemented` requirement that
   nothing cites fails, an identifier-shaped tag that designates no
   requirement fails. Line coverage says which code was executed; this one
   says which promise is demonstrated. See
   [ADR 0014](../adr/0014-registre-d-exigences.md), whose Consequences discuss
   the price of keeping it out of CI.
5. **End-to-end tests** — `make e2e`: configures and builds the `release`
   preset, then runs only the end-to-end harness (CTest label `e2e`, filtered
   with `ctest -L` rather than by test name). See
   [“Registering the end-to-end tests”](#registering-the-end-to-end-tests)
   above for the registration mechanism.
6. **Benchmarks** — `make bench`: reuses the `subedit_core` object already
   compiled by the previous step, but links its own executable
   (`subedit_bench`) — so it is not a no-op, only cheaper than a full `release`
   build. Its verdict is read, it is not binary — on purpose: the project's
   [definition of "done"](../../CLAUDE.md) requires replaying the benchmarks
   on every issue, and chaining them here is what guarantees it rather than
   relying on the memory of whoever opens the pull request.

The criterion for entering `check-local` is the same for any future addition:
useful before a pull request, but not universal enough — or too costly — to
gate every push on CI.

## Continuous integration

One workflow, `.github/workflows/ci.yml`, on `push` and `pull_request`:

- **`check`** — `ubuntu-24.04` runner, toolchain installed by the same script
  as locally, `ccache` cache, run of `make check`, coverage report uploaded as
  an artifact.
- **`commits`** — validation of the commit messages and of the PR title against
  the Conventional Commits grammar.

No external coverage service, no OS or compiler matrix: the target is Linux,
and the Windows port will come with its own issue.

## Git and GitHub

### Conventional Commits

```
<type>(<scope>): <description>
```

**Types:** `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci`,
`chore`.

**Scopes:** identical to the `area:` labels — `build`, `core`, `format`,
`text`, `cli`, `gui`, `video`, `i18n`, `ci`, `doc`. An issue and the commits
that address it thus share the same vocabulary.

Validation by a local `commit-msg` hook **and** in CI. The hooks are shell
scripts installed into `.git/hooks` by `src/scripts/install-hooks.sh` — no
dependency on a third-party hook manager.

- `pre-commit`: `clang-format` on the staged files, refusal if `reference/` is
  staged by mistake.
- `commit-msg`: validation of the grammar.

### Branches

`main` protected by a ruleset, work on `feat/…`, `fix/…` branches. Direct push
to `main` allowed for the owner — no mandatory PR at this stage, the
requirement can be raised later without changing anything else.

### Issues

Form templates for bug, story, enhancement and task. Labels and milestones are
described in [`../configuration-github.md`](../configuration-github.md),
together with the repository lock-down configuration.

## CHANGELOG

`CHANGELOG.md` at the root, in the *Keep a Changelog* format, **generated by
`git-cliff` from the commit history**. It is the direct return on investment of
Conventional Commits: the classification is already in the messages, the
generation is deterministic, and no entry can be forgotten.

`make changelog` regenerates the file. **This regeneration is part of an
issue's definition of "done"**, just like the tests.

## Documentation

| Location | Content |
| :------- | :------ |
| `docs/principes-de-conception.md` | permanent design and memory management rules |
| `docs/specs/NN-<topic>.md` | one spec per subproject, lasting design |
| `docs/adr/NNNN-<title>.md` | technical decisions and rejected alternatives |
| `docs/exigences.md` | what the binary promises, and the state of what proves it |
| `docs/manual/<executable>/` | user manual, one file per section |
| `README.md` | what the project is, why, how to build it |
| `CONTRIBUTING.md` | workflow, conventions, commands |

A spec describes a design that must stay readable afterwards; an issue
describes a piece of work that dies when it is done. The two do not overlap,
and issues point to the spec of their subproject.

The manuals are structured as one folder per executable, one file per section,
an `index.md` as table of contents. **Writing the relevant manual section is
part of an issue's work**, not of a final catch-up pass: putting the expected
behaviour into French is a design test.

The code carries Doxygen-style comments on the public API. No generation is
set up; the trigger would be a stabilised API.

## Acceptance criteria

The third criterion gave rise to a replayable script,
`src/scripts/verify-gates.sh`, exposed by `make verify-gates`: it injects a
defect of each kind, checks that the matching step fails, then restores the
sources. To be rerun after any change to `.clang-format`, `.clang-tidy`, the
compilation options or the coverage threshold — a gate one has never seen
close is only a belief.

The subproject is done when:

1. `make setup` installs the toolchain on a bare Ubuntu 24.04 machine.
2. The repository contains a `subedit_core` library reduced to a trivial
   module, its test and its benchmark, and a `subedit-cli` executable that
   calls it — enough to prove that the whole chain works end to end.
3. `make check` passes and **actually fails** when one deliberately
   introduces: a format defect, a warning, a pattern rejected by clang-tidy, a
   memory error, a drop of coverage below the threshold. Checking that the
   gates close is part of the work.
4. CI is green on GitHub and runs `make check`.
5. The git hooks reject a non-conforming commit message.
6. `make changelog` produces a consistent `CHANGELOG.md`.
7. The five ADRs are written, as well as `README.md` and `CONTRIBUTING.md`.
8. The public GitHub repository is created and configured according to
   [`../configuration-github.md`](../configuration-github.md).

### Completion

| Criterion | State | Proof |
| :-------- | :---- | :---- |
| 1 — toolchain | ✅ | `setup-toolchain.sh` run on the target machine |
| 2 — end-to-end chain | ✅ | `subedit_core`, its test, its benchmark, `subedit-cli` |
| 3 — the gates close | ✅ | `make verify-gates`, five defects injected, five failures |
| 4 — green CI running `make check` | ✅ | workflow `ci`, jobs `porte de qualité` and `messages de commit` |
| 5 — git hooks | ✅ | non-conforming message rejected, staging of `reference/` refused |
| 6 — CHANGELOG | ✅ | `make changelog`, git-cliff 2.10.1 |
| 7 — ADRs and documentation | ✅ | ADRs 0001 to 0005, `README.md`, `CONTRIBUTING.md` |
| 8 — repository configured | ⚠️ | labels, milestones and rulesets done; two settings left |

The two remaining settings have no API and are made in the web interface:
approval of fork workflows, and interaction limits. They protect against
outside interactions that do not happen yet on a repository with no
visibility; their absence blocks no work.

**Three accepted deviations** from the initial design, each justified in place
in this document:

- the presets **do not pin Ninja**;
- criterion 3 gave rise to a **replayable script** rather than a one-off
  check;
- a **third architecture invariant** was added afterwards — the scripts must be
  executable in the git index — because its absence actually broke CI. Two
  others followed it for the same reason: a version tag that does not agree
  with `project(VERSION)` would make the binary announce an outdated version,
  and **a test case name starting with a dash is read by Catch2 as one of its
  options** when CTest passes it as an argument. The latter only shows through
  CTest — hence in the gate and in CI, never when launching the test binary by
  hand — and it was paid for twice while writing the CLI before being recorded.

## Open points

To be settled in the following subprojects, mentioned here because they will
influence the code from the very first lines:

- **Error handling strategy** — exceptions, return codes or a result type.
  `std::expected` belongs to C++23: unavailable in C++20, but working with the
  GCC 13 already installed under `-std=c++23`. Choosing the result type would
  therefore mean moving the project to C++23, without changing compilers. To be
  settled in phase 1, by ADR — see [`../adr/README.md`](../adr/README.md) for
  the measured reservations.
- **Regular expression engine** — PCRE2, compatible with the Python syntax of
  Gaupol's patterns, or RE2, markedly faster but without backreferences. To be
  settled in phase 12, after measurement. **Settled by
  [ADR 0036](../adr/0036-icu-pour-les-motifs-de-correction.md): neither, ICU.**
