# 0024 — Generated screenshots, and the environment in which they are authoritative

**Date:** 2026-08-28
**Status:** accepted

Decided while writing issue #199.

## Context

The `subedit-cli` manual carries `console` blocks that `generate-manual.sh`
rewrites **by running the binary**. That is what keeps them from lying, and
that is why no example invocation is copied by hand.

The interface manual had no equivalent. #116 then #161 wrote it each time, with
the same reason: a window cannot be written in a `console` block. #161 had added
the warning — "this is the second section without a safety net, and there is no
free third one". There have been nine.

What has changed since, and makes the question askable: since #191, **the tests
show the windows they drive**. A shown window has a real geometry and a layout
that has actually run — hence something to photograph. Before, there was
nothing.

A screenshot then raises a question the `console` block did not. The output of
`subedit-cli --help` is the same everywhere; the image of a window is not. Two
machines do not have the same fonts, the same widget style, the same theme.
**A reference generated here would get promoted over there, and vice versa**:
the reference would oscillate according to who ran the command, and the
repository's diff would stop meaning anything.

## Decision

**Screenshots are generated by the same gesture as the `console` blocks —
`make manual` — and are authoritative only under the settings that the capture
program sets itself.**

Those settings are four, and the program sets them all:

| Setting | Value | Why it cannot be left to the machine |
| :------ | :---- | :----------------------------------- |
| Qt platform | `offscreen` | there is no screen in continuous integration, and a graphical session would bring its window manager |
| style | `Fusion` | the default style follows the installed desktop; Fusion is the same everywhere |
| font | `DejaVu Sans`, size 10 | the only item on this list a machine may lack |
| dimensions | fixed, in pixels | `sizeHint()` depends on the font, hence on the machine |

**The font is the only one that can be missing, so it is the only one that is
checked: the program refuses to take pictures with a substitute.** Qt silently
substitutes a missing font, and a screenshot taken under a substitute would
look exactly like a legitimate one — until the moment it got promoted on the
next person's machine.

That is what makes "where screenshots are authoritative" a **verifiable
condition** rather than a machine name. They are authoritative wherever the
program agrees to run; where it refuses, it says why and what to install.

## The mechanism, and why the repository does not swell

A screenshot versioned as generated would produce a modified binary on every
run. Three pieces avoid that:

1. the capture program **never** writes the reference: it writes
   `<name>.new.png`;
2. `compare-screenshots.py` compares the `.new` with the reference of the same
   name; above the threshold, the `.new` **replaces** the reference — git sees
   a modification, and it means something; below, the `.new` is **deleted**,
   and git sees nothing;
3. `check-screenshots.py` catches what neither of the two can see: an image the
   manual shows and nothing generates, a generated image nobody shows, a
   capture that would write the reference directly.

**The threshold has two components, and that is what makes it useful.** The
*severity* says by how much a channel must differ for a pixel to count; the
*area* says how many pixels must differ in that way for the image to have
changed. A single threshold does not distinguish antialiasing that moved
everywhere from a word that changed somewhere — the first is noise, the second
is the only change that matters.

## What the screenless platform hides — measured

**Added in August 2026, while handling issue #268**, which asked of every check
in the repository whether the tool that checks is the one that matters. For
screenshots, the answer is no by construction: they are taken by the
`offscreen` platform, and a reader of the manual has a desktop. The question
was not to change platforms — reproducibility is what holds this whole
mechanism together, and a screenshot taken on a graphical session would get
promoted on the next person's machine. The question was what the platform
hides.

The sixteen screenshots were therefore generated twice, the second time under
an X server and the `xcb` platform:

```console
$ xvfb-run -a -s "-screen 0 1600x1200x24" \
      env QT_QPA_PLATFORM=xcb build/dev/bin/subedit_screenshots --output-dir <directory>
```

**Fourteen of the sixteen differ, all far above the comparator's threshold** —
from 0.6 % to 13.6 % of the pixels. The two that do not differ by a single byte
are those of the manual window: it is only a `QTextBrowser`, and nothing it
draws depends on the platform.

| What changes under `xcb` | Where it comes from |
| :----------------------- | :------------------ |
| the toolbar and dialog button icons appear | `QIcon::fromTheme` renders nothing under `offscreen`, and setting `QT_QPA_PLATFORMTHEME` does not bring them back: it is the platform, not the theme |
| `Cancel` moves to the left of `OK`, and mnemonics get underlined | button order is a style hint of the platform theme, which `offscreen` does not provide — `offscreen` with `QT_QPA_PLATFORMTHEME=gtk3` is enough to change it |
| the current-cell rectangle disappears from the table | no window is ever *active* without a window manager |

**The same mechanism bit elsewhere, and more dearly** — issue #274. What
`QKeySequence` returns for a standard command comes from the platform theme:
without a theme, Qt falls back on an internal table where `SaveAs` exists only
for macOS and Windows, and where `Redo` starts with `Ctrl+Y`. A measuring
program run without a theme therefore concluded that "`Save As…` has no
shortcut on Linux" and that "`Ctrl+Shift+Z` does nothing" — and **the manual
was corrected towards those two statements, which are false for every user**.
On a desktop, xcb as well as wayland, the theme gives `Ctrl+Shift+S` and
`Ctrl+Shift+Z`.

The lesson is therefore not specific to screenshots: **everything Qt derives
from the platform theme differs, in a test binary, from what a user gets.** A
measurement taken under `offscreen` answers about `offscreen`, never about a
desktop — and it is a place where one believes one is measuring the program.

**This is not a reason to change platforms, and it is one to write it down.**
The manual describes words and actions, not pixels, and none of its sentences
becomes false: the buttons in a screenshot carry the same labels as those on
the reader's desktop. What needs knowing fits in one sentence — **a manual
screenshot shows the window without its desktop's icons, and with Fusion's
button order rather than the desktop's.** The question will not come up again;
it is answered here.

## Alternatives dismissed

**Versioning the screenshot directly, without a comparator.** It is the
simplest form, and it gives a repository in which every `make manual` modifies
six binaries. A real interface change would drown in it.

**Comparing the file's bytes rather than its pixels.** Tempting, since the
screenshots turned out to be byte-for-byte reproducible under the settings
above. Dismissed: reproducibility depends on a given PNG encoder, and a Qt of a
different version would rewrite the same pixels differently. The comparator
therefore reads pixels — but it compares the bytes **first**, which is not a
contradiction: two identical files necessarily carry the same pixels, and the
overwhelming majority of comparisons stop there, in a millisecond.

**Adding an image library to the toolchain.** `numpy` or `Pillow` to count
differing pixels. Dismissed: decoding the PNG subset Qt writes — eight bits per
channel, no interlacing — fits in sixty lines, and one more dependency is paid
for at every toolchain installation, on every machine, forever.

**Making CI the authority.** It is the answer of a project with many hands, and
it has a flaw here: it makes it impossible to regenerate a screenshot without
pushing. The four settings above give the same guarantee without the detour —
and if CI honours them, it is a machine like any other.

## Consequences

**`make manual` has changed in nature.** It built only `subedit-cli`,
deliberately; it now builds the interface, hence Qt. The price is that of an
incremental build which the quality gate already does anyway.

**The video pane is not photographed.** libmpv draws into an adopted native
window, outside Qt's painting: a `grab()` would render an empty rectangle. That
is the subject of #190 — with the render API, mpv would draw into a Qt widget
and the picture would become capturable. The player section therefore stays
without an image, and it is a named absence rather than an oversight.

**Doubling the screenshots per theme is done.** D4 of the phase 7 scoping
promises two screenshots per screen, light and dark; the theme came with #241,
and every screen is now photographed under both palettes — eleven pairs, the
dark one carrying the suffix `-sombre`. The mechanism took them without
changing anything: one more screenshot is one more call in the program, one
more name in the directory, one more image in the section. And
`check-screenshots.py` requires the dark one of every light one (#400), unless
exempted with a reason.

**An interface change shows in the repository's diff.** It is the main benefit,
and it is worth saying in the right place: a promoted screenshot is a review
asked of whoever pushes, not just an updated image.

## Addendum — one set per language ([#672](https://github.com/Guyot-Bertrand/sub-edit/issues/672))

Decided by the maintainer on 2026-10-13, superseding the shared set spec 15 had planned: **a
screenshot carries the window's words, so every manual tree has its own set**, with the same
file names. A translated page showing the English window would contradict its own text.

- **Layout.** English, the source, stays in `docs/manual/subedit-gui/captures/`; every other
  language lives in `docs/i18n/<lang>/manual/subedit-gui/captures/`, next to the pages that show
  it. A page shows the images of its own tree only: `check-screenshots.py` refuses a borrowed one
  (`FOREIGN`), a missing one (`BROKEN`) and one nothing produces (`FROZEN`), tree by tree, and
  `check-manual-links.py` refuses an image that does not exist.
- **Generation.** `make manual` shoots English, then every language of `src/po/LINGUAS`, with
  `subedit_screenshots --language <lang>`: the window is built under that language's shipped
  catalogue and Qt's, asked by name rather than read from the environment, and the manual window
  shows that language's tree. A language whose catalogue, ours or Qt's, is missing is refused,
  as a missing font is. A language added to `LINGUAS` gets its set from the same command, with no
  code to change; the French set is the first.
- **The program still never writes a reference.** It writes `<name>.new.png` in the directory of
  the tree, and `compare-screenshots.py` promotes or deletes, one tree at a time.
- **Fonts.** The four settings above still hold, `DejaVu Sans` included. It covers the Latin and
  Cyrillic languages; Hebrew only partly, and Chinese not at all. `he` and `zh_CN` will need a
  font that covers them (e.g. Noto Sans CJK) before their sets can be authoritative — not solved
  here, and to be settled by the issue that installs those languages.
